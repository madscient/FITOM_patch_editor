# 設計判断

選択肢があった判断だけを、1件ずつ短く記録する。読み手は開発者と AI。
「今どうなっているか」は `docs/ARCHITECTURE.md`、作業の経過は
`docs/STATUS.md` に書く。ここには作業の手順や画面の細部を書かない。

## D-番号の引き方

- コードコメントや文書にある `D-xxx` は、まずこのファイルで引く。
- このファイルに無い番号は、`docs/history/DESIGN.md` の同じ番号を見る。
  D-001〜D-058 はそこに原文がある。その中で今も効いている判断は、
  順次このファイルへ要約して移す。
- 新しい判断は D-059 から続けて採番する。番号は振り直さない。

## 書き方

```
### D-xxx: 決めたこと(1行)

- 決定: 何をどう決めたか。
- 理由: なぜそれを選んだか。
- 前提: 何が変わらない限りこの判断が成り立つか。
- 見送った案: 検討して採らなかった案と、その理由。
- 原文: docs/history/DESIGN.md D-xxx(あれば)
```

判断を覆したときは、元のエントリを消さずに「撤回: D-yyy」と1行足し、
新しいエントリを書く。

---

### D-059: 文書を読み手と役割で分ける

- 決定: 文書を次のように分ける。
  - `README.md`: エディタを使う人向け。何のツールか、ビルド、起動、使い方。
    関数名と経緯は書かない。
  - `docs/ARCHITECTURE.md`: 開発者・AI 向けの現在の構成と規約。現在形で
    書き、変わったら書き換える。
  - `docs/DECISIONS.md`(このファイル): 判断の記録。
  - `docs/STATUS.md`: 現状の要約、利用者の確認待ち、課題、直近5件の
    進捗ログ。
  - `docs/history/`: 古い文書の原文。書き換えない。
  - `CLAUDE.md`: AI の作業ルールと読む順番。
- 理由: 旧 `docs/DESIGN.md` は作業ごとの記録になっていて、判断・現在の
  構成・作業の詳細が混ざっていた。約4300行あり、人間が読む文書ではなく、
  AI が毎回読むにも重かった。`docs/STATUS.md` の進捗ログとも同じ作業を
  二重に書いていた。
- 前提: コードコメントの D-番号(82種、337箇所)の行き先が残ること。
  旧 DESIGN.md を `docs/history/DESIGN.md` に原文のまま置いて満たしている。
- 見送った案:
  - ARCHITECTURE と DECISIONS を1本にまとめる案。「今どうなっているか」と
    「なぜそうしたか」は変わる頻度が違い、同じ文書だと現在形の記述と
    経緯が再び混ざるため採らなかった。
  - 旧ログを削除して git 履歴に任せる案。コードコメントの D-番号が
    引けなくなるため採らなかった。
- 原文: なし(この判断が最初)。
