# 設計判断

選択肢があった判断だけを、1件ずつ短く記録する。読み手は開発者と AI。
「今どうなっているか」は `docs/ARCHITECTURE.md`、作業の経過は
`docs/STATUS.md` に書く。ここには作業の手順や画面の細部を書かない。

## D-番号の引き方

- コードコメントや文書にある `D-xxx` は、まずこのファイルで引く。
- D-001〜D-058 の原文は `docs/history/DESIGN.md` にある。このファイルには、
  そのうち今も効いている判断だけを要約して載せた。載っていない番号は、
  作業の記録だったものか、後の判断で覆されたもの(覆した側のエントリに
  「撤回」として番号を挙げてある)。経緯を見たいときは原文を引く。
- 新しい判断は、最後の番号の続きで採番する。番号は振り直さない。

## 書き方

```
### D-xxx: 決めたこと(1行)

- 決定: 何をどう決めたか。
- 理由: なぜそれを選んだか。
- 前提: 何が変わらない限りこの判断が成り立つか。
- 見送った案: 検討して採らなかった案と、その理由。
- 撤回: この判断で覆した D-番号と、覆した部分(あれば)
- 原文: docs/history/DESIGN.md D-xxx(あれば)
```

判断を覆すときは、新しいエントリに「撤回: D-yyy」を書き、元のエントリは
消さずに「撤回された: D-zzz」と1行足す。

D-001〜D-058 の要約では、原文に前提や見送った案が書かれていないものは
「原文に記載なし」とした。後から推測で補っていない。

### D-001: FITOM_X とは別リポジトリ・別プロジェクトにする

- 決定: FITOM_X のソースツリーに依存しない、独立した C++ プロジェクトに
  する。接点はファイル形式(profile / bank JSON)と MIDI パイプの
  プロトコルだけで、コードは共有しない。
- 理由: エディタはオフラインで動く必要があり、試聴はパイプ越しの疎結合で
  足りるので、ビルド依存として FITOM_X を要求する理由が無い。FITOM_X の
  `apps/fitom_gui` とは別のプロジェクトにする方針は利用者に確認した。
- 前提: 原文に記載なし。
- 見送った案: 原文に記載なし。
- 原文: docs/history/DESIGN.md D-001

### D-003: JSON は「読み込みは緩く、書き込みは明示的に」

- 決定: 欠けたフィールドは既定値で埋め、パースエラーにしない。書き込みでは
  正規のフィールド一式を出す。
- 理由: FITOM_X 自体の「ソフトな失敗」の設計に合わせた。往復編集の単純さを
  優先した。
- 前提: 原文に記載なし。
- 見送った案: 元ファイルの簡潔さを再現すること(狙わないと明記)。
- 撤回された: D-057(`*.hwbank.json` の書き込みだけ、チップが読まない
  フィールドを省く)
- 原文: docs/history/DESIGN.md D-003

### D-004: GUI は Dear ImGui、バックエンドは GLFW + OpenGL3

- 決定: GLFW + OpenGL3 を使う。
- 理由: FITOM_X 本体が Dear ImGui を使っているので踏襲した。バックエンドは
  利用者に3択(SDL3 / SDL2 のバックエンドを手で管理 / GLFW)を示し、
  GLFW が選ばれた。
- 前提: タッチ操作を本格的に作り込む段階で問題になれば見直す(D-005)。
- 見送った案:
  - SDL2: タッチ(明示的なマルチタッチイベント)には本来最も向くが、vcpkg の
    imgui ポートが SDL2 用バインディングを提供しなくなっていた。
  - SDL3: vcpkg が公式にバインディングを持ち最有力だった。不採用の理由は
    原文の文が途中で切れていて分からない。
  - GLFW の欠点として、ネイティブのマルチタッチ API が無く OS のマウス
    エミュレーションに頼ることを認識したうえで選んでいる。
- 原文: docs/history/DESIGN.md D-004

### D-005: タッチ操作で GLFW の限界に当たったら SDL3 を検討する

- 理由: D-004 で GLFW を選んだことの将来の手当て。
- 前提: マルチタッチが必要になった場合の方針。
- 見送った案: 原文に記載なし。
- 原文: docs/history/DESIGN.md D-005

### D-006: サードパーティ依存は vcpkg マニフェストモードだけ

- 決定: 依存は `vcpkg.json` で宣言し `find_package` で解決する。リポジトリに

  リポジトリに持ち込まない構造にして、この問題を避けた。
- 前提: 原文に記載なし。
- 見送った案: git submodule、CMake の `FetchContent`(当初は nlohmann-json を
  これで取っていた)。
- 原文: docs/history/DESIGN.md D-006

### D-012: アウトラインはバンク一覧だけにし、中身は別画面で見る

- 決定: アウトラインにはバンク・キットの一覧(名前・番号・件数)だけを出す。

### D-013: ADPCM 系の「パッチ一覧」は `*.pcmbank.json` が指す `entries[]`

- 決定: ADPCM-B / ADPCM-A / PCM-D8(後に SSGS-ADPCM も)の音色は、
  `*.pcmbank.json` が参照する `adpcm_json`(adpcm_packer の出力)の
  `entries[]` で、配列の添字(0始まり)がそのまま `patch_prog` になる。
  これを `fpe::PcmBank` として HwBank・SampleZoneBank と別に持つ。
  `entries[]` を直接持つファイルはそちらを優先し、`adpcm_json` は
  pcmbank 自身のディレクトリを基点に解決する。
- 理由: 利用者から直接確認した仕様(エンドユーザーは直接編集しないが、
  ドラムキットから参照するので一覧が要る。FITOM_X もそう取得している)。
  `config_schema/pcmbank.schema.json` とも整合する。
- 前提: 原文に記載なし。
- 見送った案:
  - 中身の CRUD API。エンドユーザーが編集しないので設けない。ただし
    「名前を付けて保存」で自己完結したコピーを作るため、保存と
    `adpcm_json` / `bin_file` のコピーには参加させる。
  - 実データの `adpcm_json` のパスの不整合を推測で直すこと。解決の基点が
    2通り考えられ、FITOM_X 側の意図を断定できないため、警告に留める。
- 撤回: D-011(ADPCM-B/A・PCM-D8 を通常の HwBank として読むとした部分。
  AWM だけを SampleZoneBank にする部分は維持)
- 原文: docs/history/DESIGN.md D-011, D-013

### D-014: 新規バンク作成ダイアログ

- 決定: アウトラインに「新規バンク作成」を置く。
  - 種別(レイヤード / デバイス / パフォーマンス / ドラムキット)、バンク名、
    ファイル名の語幹を入力させる。ディレクトリと接尾辞は種別から作る。
  - デバイスはチップ系統、ドラムキットは routed / direct も選ばせる。
  - バンク番号は既存の最大値+1で自動採番する。
  - OK でその場でファイルを書く。
  - チップ系統から AWM、ADPCM 系、SD1 / MA3 / MA5 / MA7 を除く。
- 理由:
  - 除外: これらを通常の HwBank として作ると、次の読み込みで別の形として
    解釈され、どの形にも合わないファイルになる。
  - 即保存: 依頼の文言が「バンクファイルを作成」だった。
  - 自動採番と種別に連動する入力: 依頼が明示したのは3項目だけで、文面が
    種別でダイアログが変わる設計を示していた。
- 前提: 原文に記載なし。
- 見送った案: 番号を入力させること、利用者に追加で確認すること、保存ボタンを
  待つこと。
- 原文: docs/history/DESIGN.md D-014

### D-015: パッチ編集はモードレスで複数開けるウィンドウにする

- 決定: 編集ウィンドウはモードレスで、複数を同時に開ける。`AppState` に
  関係なく毎フレーム描く。ウィンドウは `{バンクの添字, prog}` だけを持ち、
  実体は毎フレーム引き直す。同じパッチを再度開こうとしたら既存の
  ウィンドウを前に出す。試聴は FITOM_X の内部パイプへ、CC#0 / CC#32 /
  プログラムチェンジ、パラメータ上書きの SysEx、ノートオンの順で送る。
- 理由: 利用者の要件(パッチ一覧から選ぶと編集画面が開き、モードレスで
  複数開ける)。実体を引き直すのは D-012 と同じ考え方。
- 前提: エンベロープ波形の表示は編集の目安で、チップのエンベロープを
  再現するものではない。
- 見送った案: 原文に記載なし(最初は Device だけを対象にし、他の種別は
  後に D-036 / D-037 / D-038 で作った)。
- 撤回された: D-018(MIDI 出力へのフォールバックを見送った部分)
- 原文: docs/history/DESIGN.md D-015

### D-018: 試聴は FITOM_X のパイプを優先し、無ければ RtMidi で MIDI 出力する

- 決定:
  - FITOM_X の内部パイプに繋がらないとき、RtMidi(vcpkg の `rtmidi`)で
    MIDI 出力ポートへ送る。
  - トランスポートを3層に分ける: バイト列の組み立て(`MidiMessages.h`)、
    各トランスポート(`MidiPipeClient` / `RtMidiOutput`)、それを束ねる
    `PreviewOutput`。
  - プリファレンスのダイアログを置く。MIDI ポートはダイアログを開くたびに
    列挙し直す。
  - コマンドライン引数のプロファイルはプリファレンスより優先するが、
    プリファレンスの内容は書き換えない。
  - プリファレンスの読み込み失敗は既定値にし、保存失敗はエラー表示する。
- 理由:
  - RtMidi: C++ から直接使えるクロスプラットフォームの定番で、vcpkg で
    解決できる(D-006)。
  - 3層: パイプ経路と MIDI 経路にバイト列の組み立てを重複させないため。
    プライベート SysEx は一般の MIDI 機器では無視されるので、経路を問わず
    送ってよい。
  - ポートの毎回の列挙: ポートは実行中に増減する。
  - 保存失敗だけ表示: 利用者に伝える価値がある。
  - 引数の扱いは利用者の要件どおり。
- 前提: 原文に記載なし。
- 見送った案: `MidiPipeClient` に RtMidi の分岐を埋め込むこと。
- 撤回: D-015(MIDI 出力へのフォールバックを見送った部分)
- 撤回された: D-020(保存先)
- 原文: docs/history/DESIGN.md D-018

### D-026: キオスクモード(1つのパッチだけを編集して終わる起動)

- 決定: 起動引数で対象のパッチを指定すると、その編集画面1枚だけを
  ビューポート全体に固定して開き、閉じたらプロセスを終える。対象は
  プロファイル全体を読んだうえで、バンクファイルを `fs::equivalent()` で

- 理由: FITOM_X からの起動を想定した利用者の要件。バンクファイル単体を
  読まないのは、HwBank の JSON にチップ種別が無く、プロファイルの group
  からしか決まらないため。
- 前提: 原文に記載なし。
- 見送った案: 枠(タイトルバー)の無いウィンドウ。「編集の完了」を伝える
  閉じるボタンの代わりが要り複雑になるので、利用者が許した「常に全体に
  ドッキングした状態」を採り、閉じるボタンを残した。
- 撤回された: D-029(失敗の通知方法)、D-039(引数の形式)
- 原文: docs/history/DESIGN.md D-026

### D-027: 「登録」ボタン、差分の SysEx、閉じるときの再送

- 決定:
  - パッチ編集画面に「登録」を置き、保存する。
  - パラメータを変えたら、変わった部分だけを SysEx で送る。
  - 編集画面を閉じるとき、最後に登録した内容を全部送り直す。
- 理由:
  - 利用者の要件。
  - FITOM_X のパラメータ上書き SysEx は、含めたキーだけを変える仕様で、
    差分で送ることを最初から想定している。
  - 閉じるときに送り直すのは、登録しないまま試聴に反映させた編集を、
    FITOM_X 側でもディスクの内容に戻すため。
  - 保存がワークスペース全体なのは、単一バンクを保存する API が無いため。
- 前提: 原文に記載なし。
- 見送った案: 原文に記載なし。
- 原文: docs/history/DESIGN.md D-027(登録で閉じる挙動は D-048、FITOM_X の
  メモリへの反映は D-049)

### D-029: 起動時の失敗はメッセージボックスで知らせる

- 決定: 標準エラー出力に加えて、ネイティブのメッセージボックスを出す
  (`showFatalErrorBox()`)。Windows では UTF-16 に変換して `MessageBoxW` を
  使う。キオスクモードの引数検証だけでなく、通常起動の初期化失敗にも使う。
  起動後のエラーは GUI 内のポップアップで出す。
- 理由: FITOM_X は子プロセスを並行して動かすだけで、終了コードを待たない
  (利用者の指摘)。`MessageBoxA` に UTF-8 を渡すと、日本語環境のコード
  ページで解釈されて文字化けする。通常起動も FITOM_X から非対話的に
  起動されうる。
- 前提: 原文に記載なし。
- 見送った案: 終了コードだけで知らせる(D-026 の当初案)、`MessageBoxA`。
- 撤回: D-026(終了コードで知らせるとした部分)
- 原文: docs/history/DESIGN.md D-029

### D-030: FITOM_X が割り当てる MIDI チャンネルを使う

- 決定: 接続直後に FITOM_X が送るハンドシェイク SysEx を読み、そこで
  割り当てられたチャンネルで送る。ハンドシェイク前に切断されたら
  「接続数オーバー」として、未起動と区別する。接続数オーバーは毎フレーム
  確かめ、メッセージボックスを出して終了する。プリファレンスの MIDI CH は
  RtMidi のときだけ使う。
- 理由: FITOM_X 側で、複数のエディタを同時に動かすためのチャンネル割り当て
  プロトコルが策定された(`docs/plugin-midi-pipe.md` 4.1)。接続数オーバーで
  終了するのは利用者の要件。
- 前提: 原文に記載なし。
- 見送った案: 原文に記載なし。

### D-050: JSON を経由しない音色(OPLL 系 ROM 音色、内蔵リズム)を解決する

- 決定:
  - FITOM_X が内部で作る音色の表と番号の規約を `fpe::BuiltinVoices` に移植し、
    データモデル層に置く。
  - ROM 音色の名前は、参照元の CC#0 ではなく `hw_prog` から読み解く。
    ピッカーは配列の添字ではなく `(変種 << 4) | 音色番号` を書く。
  - カテゴリ一覧は読み込んだバンクから作る方式のまま、足りないカテゴリだけを
    補う。
  - OPLL 系の JSON のバンク0はピッカーに出さない。
  - 内蔵リズム(0x70)は ToneLayer のピッカーに出さない(表示の解決はする)。
  - どちらも「編集」ボタンを無効にする。
- 理由:
  - データモデル層に置くのは、FITOM_X のデータモデルの一部であり、ctest で
    回帰テストできるため。
  - `hw_prog` から読むのは FITOM_X がそうしていて、実データもそれに依存
    しているため。生の添字を書くと別のチップの音色が鳴る。
  - バンク0を出さないのは、FITOM_X が常に ROM 音色へ振り向けるので、
    選べても鳴らないため。
  - 0x70 を出さないのは、ToneLayer の voice_patch_type がスキーマで
    0x01〜0x6F に限られ、エディタがスキーマ違反のデータを新しく書くべき
    ではないため。
  - 編集を無効にするのは、どちらも JSON 上に編集できる実体が無いため。
- 前提: 原文に記載なし。

### D-057: チップ別パラメータ定義は FITOM_X の `spec/chip-capabilities.json` を実行時に読む
